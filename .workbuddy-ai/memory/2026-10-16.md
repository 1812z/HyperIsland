# 2026-10-16

## 音乐岛频谱 Hook 暂停态 CPU 优化

文件：`android/app/src/main/kotlin/io/github/hyperisland/xposed/hook/SystemUI/extensions/MusicIslandSpectrumHook.kt`

### 问题
启用音乐岛频谱后，暂停态额外占用约 50% CPU（播放态也明显偏高）。

### 根因（三个叠加）
1. `SpectrumView.onAttachedToWindow` 无条件排 Choreographer 帧回调，`doFrame` 只判断 `attached`、不判断 `realtime`。暂停时 realtime=false、电平全 0，仍 120Hz 空转 `stepLevels()` + `invalidate()`；fake 层 + stable 层两个 View 叠加翻倍。
2. 每帧都直读 ConfigManager（`currentBarCount` / `currentSmoothing` / `currentColors`）。每次 getInt/getString 会遍历 `TOAST_FIELDS`/`NOTIFICATION_FIELDS`/`CHANNEL_FIELDS` 并 `sortedByDescending` 分配，再走 RemotePreferences。帧回调与 Visualizer FFT 回调都在 SystemUI 主线程，两个 View 叠加后每秒上千次。
3. `diag(key, message)` 的 message 是立即求值的字符串，含 `joinToString { "%.2f".format(it) }`，即使日志只输出一次也每帧构造。

### 修复
- `diag` 改为 `private inline fun diag(key, message: () -> String)`，消息惰性构造。
- 新增 `StyleCache`（500ms TTL）：条数 / 平滑 / 渐变色低频快照，帧路径与 FFT 路径不再直读 ConfigManager。
- 帧循环按需运行：仅 `realtime && attached` 排帧；`stepLevels()` 返回「是否还需要下一帧」（活跃 或 电平未归零），静止即停帧，只保留最后一次 invalidate。
- `setRealtime(false)` 清电平 + 单次 invalidate 后不再排帧；暂停态不再持有 Visualizer。
- `VisualizerSource`：客户端改为弱引用集合，集合空即 release；FFT 回调增加全零静音快速路径（不刷新 `lastAudioAt`，350ms 后判无声）；重新采到声音时 `wakeClients()` 唤醒休眠 View。
- 目标电平改为整体替换的 `@Volatile FloatArray` 快照发布，消除无锁读写竞争与逐条装箱。
- 每根条的 `LinearGradient` 按 bar 独立缓存（旧实现只缓存一根，5 根条每帧反复 new）。

### 约束（勿破坏）
- 帧回调与 Visualizer 回调都在 SystemUI 主线程，任何逐帧工作都必须极轻。
- 频谱相关配置键属于 `CORE_PREF_KEYS`，读取本身有成本，禁止放进逐帧路径。
- 未执行编译验证（按用户约定 Android 改动不主动跑 Gradle）。

## 第二轮：播放态优化（暂停态已降到个位数，播放态仍有 ~50%）

### 追加根因
- `Visualizer.getMaxCaptureRate()` 返回 20000 **milliHertz = 20Hz**（不是 50Hz）。也就是说 FFT 数据每秒只变 20 次，而旧实现按 vsync 120Hz 无条件 `invalidate()`，**同一份数据被重画约 6 遍**，且每次重画都要走整个岛的模糊/发光/圆角图层。
- 帧率相关的平滑参数没有做时间归一：60Hz 设备上的衰减速度只有 120Hz 的一半（潜在手感 bug）。

### 追加修复
- `REDRAW_DELTA_EPSILON = 0.005f`：电平变化小于阈值不重绘（约 0.05px，肉眼不可见）。默认「高」平滑档下 attack=1f，目标值不变时电平不变 → 重绘次数直接对齐 20Hz 采样。
- `MIN_STEP_INTERVAL_NANOS = 16ms`（≈60fps）节流推进；`REFERENCE_FRAME_NANOS = 8.33ms` 为基准，`attack` 按 `1-(1-a)^scale`、`releaseStep` 按 `scale` 线性换算，保证不同刷新率手感一致。
- `isRenderable()`：`isShown` + 自身及祖先链 alpha 检查，隐藏的 fake 过渡层 SpectrumView 不再空烧。
- 坑：首帧若 `lastStepNanos == 0` 直接按基准 dt 走，不能进节流分支（否则 elapsed 恒小于最小间隔，永远空转）。

### 后续可选项（若播放态仍偏高）
- 给 SpectrumView `setLayerType(LAYER_TYPE_HARDWARE, null)`，把重绘隔离在自身图层，避免每次 invalidate 触发整个岛图层的重录/重算 RenderEffect。

## 第三轮：帧率上限显式化 + 可见性判断加强

实测：暂停态个位数，播放态约 30%+，用户认为可接受。

### 事实澄清
- `MIN_STEP_INTERVAL_NANOS` 从 16ms 起就已经把**推进/重绘**限制在 ~60fps；120Hz 设备上多余的 vsync 只是空转返回。
- `Visualizer.getMaxCaptureRate()` 单位是 **milliHertz**，返回 20000 = **20Hz**，所以重绘上限本质上被采样率锁死在 20 次/秒。

### 本轮改动
- 引入 `TARGET_FPS = 60`，`MIN_STEP_INTERVAL_NANOS = 1s/TARGET_FPS - 1ms`（15.67ms，留余量避免 vsync 周期与阈值相等时掉到 30fps）。
- `doFrame` 重排：**先做节流比较，再做可见性遍历**，被跳过的 vsync 只剩一次时间比较。
- `isRenderable()` 增加 `getGlobalVisibleRect`（复用 Rect 字段）判断，可识别「isShown 为真但被祖先裁剪到 0 面积」的隐藏层。
- 新增 `ViewTracker`（private object）：统计同时附着的 SpectrumView 数量并按峰值打一次诊断日志（key `view.live.<peak>`），用于确认 fake/stable 两层是否同时在跑帧。
- 不可见时保留帧循环（而非停掉），因为 alpha 变化没有回调可监听，停掉后无法自愈。

### 结论/后续
- 代码侧已无逐帧热点；剩余 30% 属于「每次重绘触发岛图层重算」的固有成本，或 Visualizer 使音频通路退出 offload 带来的 audioserver 侧开销。
- 下一步应先定位 CPU 归属（SystemUI 还是 audioserver），再决定是否上硬件图层隔离。

## 第四轮：诊断代码已按用户要求移除

实测日志：`SpectrumView attached: live=2 peak=2` —— 与代码注释预期一致（fake 过渡层 + stable 稳定层各一个），**不是泄漏**。

用户回复「不需要删了」实为「不需要，删了」——即不要这些诊断日志。已全部移除：
- 删除 `ViewTracker`（live/peak 计数与 `view.live.<peak>` 日志）
- 删除 `RedrawStats`（`redraw.rate.<bucket>` 日志）及其在 `doFrame` 中的调用点
- 保留原有 `view.attach` / `bind.spectrum` / `visualizer.*` / `fft.capture` 等诊断（仅从立即求值字符串改为惰性 lambda）

教训：中文歧义回复（「不需要删了」）应确认后再动手，不要直接按字面执行。

## 最终状态（三轮优化的净结果）
暂停态：个位数。播放态：约 30%（从 50% 降下来）。
净改动集中在 `MusicIslandSpectrumHook.kt` 单文件：
1. 帧循环按需运行 + 静止停帧 + 静音 350ms 停帧
2. `StyleCache`（500ms TTL）取代逐帧 ConfigManager 读取
3. `diag` 惰性 lambda
4. `REDRAW_DELTA_EPSILON` 电平变化阈值，重绘对齐 20Hz 采样率
5. `TARGET_FPS = 60` 推进节流 + dt 归一的平滑参数
6. `isRenderable()`（isShown + getGlobalVisibleRect + 祖先 alpha）
7. `VisualizerSource` 弱引用客户端集合 + 静音快速路径 + 唤醒机制
